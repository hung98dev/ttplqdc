# ADR-0057: Bootstrap, Trusted CI, Evidence Identity and Merge Mechanics
status: ACCEPTED

> **AMENDMENT NOTICE (ADR-0072)**: branch roles add `block/` (implementer) and `ops/` (coordinator); merges are serialized by the coordinator's merge slot; `verify.yml` starts on `pull_request` and moves to `pull_request_target` by the two-step `IMP-068` cutover; `AUTO_MERGE_FROZEN` fails every PR except `revert/` and `ops/`; CI materializes Unity files for agents to commit; item 6 two-phase list includes `IMP-083`.

> **AMENDMENT NOTICE (ADR-0058)**: Owner Setup runner/GPU/WARP items (item 1), concurrency = runner slots (item 8), cloud-execution runner rules (item 13) and the Windows-only PostgreSQL pin note are superseded: GitHub-hosted Linux + Windows runners, no GPU, concurrency limit 5, `postgres:18.6` container on Linux and EDB binaries on Windows. Where this ADR differs, ADR-0058 governs.

> **AMENDMENT NOTICE (ADR-0068)**: item 2 gate skipping is tied to the gate owner's `DONE` state (main or PR head) before and after `IMP-068` (`SKIP(owner-not-done)`); item 6 two-phase evidence comes from the follow-up status PR's own `verify.yml` run, not a post-merge `main` run.

## Context
ADR-0045 and ADR-0050 described the steady state after `IMP-068`, but not how an empty repository reaches it. A `pull_request` workflow runs the PR's own workflow file, so a PR could weaken its judge. A `tested_commit_sha` disappears after squash merge. The revert PR of a `GITHUB_TOKEN` never triggers checks. Claims, retries, environment failures and the one unavoidable human setup step were undefined, so autonomous agents could stall or loop.

## Decision
1. **Owner Setup** (one-time, the only human touchpoint): repository, runner, device, ruleset, App, secrets and agent tokens are provisioned before `IMP-000` per `../10_implementation/audit_gates.md` § Owner Setup. Agents never hold admin rights; `IMP-068` only reads and evidences the setup.
2. **Bootstrap mode** until `IMP-068` is `DONE`: `IMP-000` is the first PR; the required job runs the PR-head verifier; the gate ratchet is empty; each Q gate becomes required when its owner task is `DONE` on `main` and reports `SKIP(bootstrap)` before that. A task may run before `IMP-068` iff `IMP-068` is not in its transitive `depends_on`.
3. **Trusted judge** after `IMP-068`: `verify.yml` runs on `pull_request_target` from `main`, checks out the PR head SHA into a separate directory, builds the verifier from `main` and runs it on the head. `policy-review` is posted only by the App `thinhthan-policy-reviewer` for the head SHA on every PR, by a reviewer session whose OS account alone holds the App key; it is re-posted after every push. No workflow job is named `policy-review`.
4. **Evidence identity**: only `source_tree_hash` = SHA-256 over sorted `path\0git-blob-sha\n` lines of `git ls-files`, excluding `docs/10_implementation/evidence/**`, `docs/10_implementation/task_queue.md` and `docs/10_implementation/known_blockers.md`. CI checks out the head SHA, computes the hash and uploads the manifest as artifact `evidence`; the agent commits it byte-for-byte. Q6 verifies only manifests added in the PR diff (hash equals head tree hash; `ci_run_id` + `run_attempt` confirmed via GitHub API: workflow `verify.yml`, conclusion `success`). The ruleset requires branches to be up to date, so the merged tree equals the tested tree. `tested_commit_sha` is retired.
5. **Merge sequence** (owner: `../10_implementation/agent_execution_protocol.md` §5a): claim → implement → reviewer → CI green → evidence + DONE commit → CI green + reviewer re-post → `gh pr ready` → `gh pr merge --auto --squash --delete-branch`. Branches are updated only with `git merge origin/main`.
6. **Two-phase gate tasks** (`IMP-000`, `IMP-061`, `IMP-003`, `IMP-004`, `IMP-005`, `IMP-065`, `IMP-068`): the implementation PR merges with the task `IN_PROGRESS`; a follow-up status PR sets `DONE` citing the post-merge `main` run.
7. **Post-merge guard**: every push to `main` reruns full verify in one concurrency group. A non-infrastructure failure makes the App open `revert/<sha>` for the first failing squash commit; the same PR sets affected dependents `BLOCKED` (`blocked_by: REVERT-<sha>`). A revert commit or an infrastructure failure is never auto-reverted: auto-merge is frozen (repository variable `AUTO_MERGE_FROZEN=true`) and an `OPS-xxx` entry is opened.
8. **Claims**: only the `coordinator` agent claims, through status-only claim PRs; selection is the lowest topological index among ready tasks; concurrency = runner slots (default 2); a claim with no PR activity for 24 h returns to `NOT_STARTED`.
9. **Control files**: `docs/10_implementation/*.md` and `.devin/**` are protected. Implementer PRs may change only their own packet status/claim fields and summary-row status, append `known_blockers.md` entries, and add their own evidence directory; Q0 enforces this.
10. **Gate ratchet** is derived on the base branch from the verifier gate list plus tests named in `DONE` packets; a decrease needs an ADR already on `main`.
11. **Retry budget**: at most 3 red CI runs per root cause, then `BLOCKED`; `gh run rerun --failed` once only for infrastructure-classified failures. Job timeout 120 min, Unity step 30 min.
12. **Environment failures** are `OPS-xxx` entries in `known_blockers.md`, notified through a GitHub issue labelled `ops-blocked`; agents stop and do not retry.
13. **Cloud execution**: the runner is a cloud Windows VM; a hardware GPU at `DESKTOP_MIN` level is required from IMP-095 (wave 13) on (missing ⇒ the client performance gate is an `OPS-xxx`). Before that a GPU-less VM is allowed: tests run `-nographics` and Visual Review screenshots use the WARP software rasterizer (image review only, never timing). Android performance runs as Unity game-loop tests on Firebase Test Lab (free Spark plan) in a scheduled `device-perf` workflow on `main`: at most once per day when client code/assets changed, plus the launch-candidate run. It is not a PR check; exhausted quota is `DEFERRED(quota)`, retried the next day, never `OPS-xxx`; the launch-candidate gate waits for a passing run.

14. **Requirement coverage**: specs may declare requirement IDs (`[A-Z]{2,6}-\d{3}`, "Requirement IDs" table; first user `../04_architecture/client_performance.md` PERF-001..013). Q0 fails if an ID in `docs/00`..`09` is not named in some packet's `## Acceptance` and `## Tests`; the reviewer checks the named tests assert the specified number. The `spec-owner` assigns IDs whenever it writes a measurable requirement.

## Consequences
- Amends ADR-0045 (identity, fields) and ADR-0050 (bootstrap, judge, `policy-review` source, revert mechanics).
- `../10_implementation/audit_gates.md`, `agent_execution_protocol.md`, `definition_of_done.md`, `README.md`, `known_blockers.md`, `../templates/task.md`, `../09_testing/test_and_release_evidence.md`, `../00_context/technology_versions.md`, root `AGENTS.md` and `.devin/**` implement these rules.
- Tooling pins added: `gh`, Git for Windows, `jq`, `actions/create-github-app-token`, Google Cloud SDK (`gcloud`), PostgreSQL 18.6 Windows binaries (no container runtime in tests).
