# ADR-0070: Durable Restart Safety, Relic Expiry, Erasure Ledger and Entity Class Budgets
status: ACCEPTED

## Context
The round-3 data/ops review of ADR-0065/0066 found: relics in stopped channels were never expired, so a stale `relic_active` blocked world-wide INSTANCED/seasonal relic spawns; a shutdown flush timeout lost server-originated durable commands while claiming clients would retry them; the erasure ledger could miss an entry on a crash after commit, had two formats and could not be replayed against a restored non-pending account; guild leadership at erasure could pass to a sibling character of the same account; the refund score overwrote any account status (including pending deletion and the tombstone); the tombstone broke the 3-characters rule; erasure steps did not follow the lock order; `accounts.created_at` stayed after erasure; auction-listing retention could not execute; sharding and forced-placement channel choice disagreed; the entity budget ignored Spirit Surge and boss adds; the partition gate named the wrong load scenario; `PERF-002` still counted software rasterization; security alert history had no store; ops tarballs had no URL; backup key/URL formats were undefined; several columns were untyped; server-job IDs had no persistence rule; one bad WorldConsequence row could close every channel start.

## Decision
- **Relic activity and expiry:** a relic is active iff `relic_active AND expires_at > now()` everywhere. A Durable-owned sweep (60 s, marker-first lock order, batch <= 256) expires relics of stopped channels; partitions load only their own rows and quarantine only themselves on unknown content IDs.
- **Durable outbox journal:** on `SHUTDOWN_FLUSH_MAX` expiry the remaining queue is journaled to `DURABLE_OUTBOX_DIR` (local disk, CRC32C records, fsync + rename) and replayed through idempotent handlers before boss schedule load, chest settlement, WorldConsequence loads and readiness. Crash semantics are unchanged.
- **Erasure:** whole lock set in priority order first; `LEDGER_REPLAY` mode without the pending precondition; successor only from other accounts, else disband; `created_at` overwritten and guard/review columns cleared; `pending_erasure_ledger` written in the transaction and PUT by a sweeper as `erasure-ledger/<operation_id>.json` (format_version 1).
- **Accounts:** refund score suspends only `ACTIVE` accounts; the tombstone is exempt from the 3-characters limit.
- **Retention:** auction listings keep `ended_at` of their latest state; `SOLD` listings with `PENDING` proceeds are not purged.
- **Placement:** automatic = most populated running channel < 18, else start the lowest-index stopped channel; forced = preferred (< 22), running < 18, stopped, running < 22, then pending.
- **Entity budget:** `MAX_ENTITIES_PER_CHANNEL = 100` = 22 players + 42 spawn-group + 12 event + 8 boss (copy + 7 adds) + 16 transient; each class limited only by its own budget; players never refused. Load scenario 18 covers it; new scenario 19 forces all 720 partitions for the partition gate.
- **PERF-002:** main-thread CPU excluding every rendering marker, Editor PlayMode under xvfb/llvmpipe, `-job-worker-count 2`, `LP_NUM_THREADS=1`, 4-vCPU hosted runner.
- **Ops:** `security-queue` alerts are stored as `audit_events` via the admin listener webhook (3 years); ops tarball download URLs pinned; `BACKUP_STORAGE_URL` = `s3://bucket/prefix?region=&endpoint=`, two-line credentials file, `PGBACKREST_REPO1_CIPHER_PASS` as the only cipher-key source.
- **IDs and schema:** server-job `operation_id` = UUID v5 over `SERVER_JOB_NAMESPACE_UUID` and `"<family>:<job_key>"`; typed columns and CHECKs for `reward_claim_lines`, `guild_storage_audit`, `world_consequence_relics`, `region_di_tich_markers`.
