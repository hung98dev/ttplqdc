# ADR-0011: PostgreSQL Relational Persistence Model
status: ACCEPTED

## Context
The Go backend needs durable transactional state for characters, items, currencies, rewards, guilds, Auction, authentication/session metadata, and idempotent operations. The game also has high-frequency live simulation that must not turn PostgreSQL into a tick/state bus.

AI implementation agents need one persistence shape so they do not independently choose an ORM, event-sourced model, document-first JSONB model, or database-per-feature architecture.

## Decision
- PostgreSQL 18.6 remains the single canonical durable database at launch.
- Go accesses PostgreSQL through pinned pgx/v5 and explicit SQL. No ORM is selected.
- Durable gameplay state is relational and normalized around explicit aggregate ownership and foreign/unique/check constraints.
- Query-critical/authority-critical fields use typed relational columns. JSONB is allowed only for bounded versioned payloads where relational querying/constraints are not required for correctness.
- Public/durable entity IDs use PostgreSQL `uuid` values generated by the Go server as RFC 4122 UUID v4 using `crypto/rand`; no UUID package dependency is required.
- Static content IDs remain immutable ASCII string IDs owned by the content bundle.
- Runtime-only entity IDs are scoped to the simulation owner/lifetime and are not reused as durable identity.
- Retriable value mutations use a stable UUID operation ID plus a durable uniqueness/result record.
- Default transaction isolation is PostgreSQL READ COMMITTED with explicit row locking/version predicates/constraints. SERIALIZABLE is used only for a documented operation that cannot be expressed safely with bounded locks/constraints.
- Transactions are short and never wait on client input, network RPC, or long-running simulation.
- High-frequency movement/combat state remains in memory; durable recovery persists only the state required by owning save/recovery rules.
- Schema changes use the pinned golang-migrate tool and expand/contract deployment rules.

## JSONB Boundary
Allowed examples:
- immutable/versioned audit metadata,
- bounded diagnostic context,
- a schema-versioned snapshot that is not independently mutated/query-authoritative.

Not allowed as an excuse to avoid modeling:
- currency balances,
- item ownership/location,
- inventory/equipment slots,
- quest completion/progression flags,
- guild membership/roles,
- Auction state/escrow/proceeds,
- Reward Claim state,
- session/revocation truth.

If a JSONB field becomes part of an ownership/value invariant, migrate the required fields into typed relational columns.

## Consequences
- Database invariants remain inspectable and testable.
- Idempotency and ownership races can rely on PostgreSQL constraints/locks instead of process-local timing.
- UUID generation does not add another runtime dependency.
- Explicit SQL requires more deliberate schema/query design but avoids hidden ORM transaction/query behavior.
- The model can later be partitioned/read-replicated where measured load requires it without changing gameplay authority.

## Invariants
```text
database = PostgreSQL 18.6
driver = pgx/v5 pinned by technology_versions.md
ORM = none
durable public/entity id = UUID v4 generated server-side
static content id = immutable ASCII string
default isolation = READ COMMITTED
value mutation = transactional + idempotent
JSONB cannot replace relational ownership/value invariants
simulation tick state != database state bus
```
