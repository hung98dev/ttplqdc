# Personal Data Register & Retention Schedule
status: LOCKED

## Scope

Canonical mapping of personal-data categories to tables/columns and the **single canonical retention schedule** (ADR-0065). `data_protection.md` owns the legal framework, category definitions and request handling and references this file for periods. The erasure transaction itself is canonical in `../06_data/data_model.md` § Account Erasure. Executing task: `IMP-056`.

Processing framework: Luật 91/2025/QH15 và Nghị định 356/2025/NĐ-CP; financial-record retention basis: Luật Kế toán 88/2015/QH13 Điều 41. A category letter is not a blanket legal exemption. The purpose/basis and bounded retention below apply to each row family; the DPO documents any case-specific legal restriction on erasure or disclosure.

A purge job per row family runs daily in bounded batches; a row is eligible when `now >= deadline`, never before. Calendar-year/month additions use UTC, preserving time of day and clamping an invalid day to the final day of the target month; days are then added in UTC. Eligibility does not authorize destroying referenced value-holding rows. Backups follow `../08_scale_ops/backup_recovery.md`; § 1.2 owns the erasure-metadata cleanup gate.

### 1.1 Restricted Field Inventory, Purpose and Scope

Grouped rows below enumerate every field, including keys and timestamps. Collection/access scope is purpose-limited: authenticated moderation operators and the DPO for reports, authorized operator-management personnel and the DPO for operators, and the erasure worker/recovery operators/DPO for erasure metadata. None is a public audit feed. Report retention supports moderation/safety and evidence continuity (legitimate interest, with a case-specific legal obligation only when documented); operator credentials support secure access (contract/security), operator identity supports administrative accountability (legitimate interest). Erasure metadata supports compliance with erasure and prevents restoration of erased personal data (legal obligation under the personal-data framework), not financial-record retention.

G receipt processing uses the existing gameplay-operation contract and legitimate interest in economy integrity/idempotent recovery. It is not a legal-hold exception or a new category; its explicit pending/reference hold prevents data loss, and its terminal purge remains anchored to the original replay horizon.

`account_id_hash` uses the preserved secret `ERASURE_LEDGER_SALT` and can be matched to an account by authorized recovery; it is **pseudonymous**, not anonymous. UUID-only report/operator/audit links and reporter notes also remain personal where re-identification is possible. Removing account FKs permits the residual account-row purge; it does not remove these restricted processing obligations. No category renaming or hash transformation permits an earlier purge or broader disclosure.

### 1.2 Canonical Erasure-Metadata Cleanup Gate

The same gate applies to completed `erasure_intents` and their external PREPARED objects. Pending intents/objects never expire. A separate janitor may delete only when all are true:

1. Independent database completion evidence exists for the exact operation/hash/preparation metadata and its fixed `completed_at`. Object state PREPARED, age, a missing intent, or failure to find an account is not completion proof.
2. `now >= completed_at + 6 calendar months + 30 days` (calendar-month addition first, then days; UTC rules above).
3. No retained restore point has a restore-as-of timestamp **earlier than** `completed_at`; the complete current backup catalog is verified, not merely its configured retention.

Missing completion/backup evidence, incomplete enumeration, database loss or a recovery cordon blocks cleanup. The janitor checks both databases/backup evidence under the operations maintenance fence in `backup_recovery.md`; the primary writer cannot delete/overwrite objects. Deleting the database intent before verifying the corresponding object cleanup must not discard the only completion evidence: retain the intent until object deletion is confirmed, then delete it, with retries verifying the same key is absent. A restore point exactly at completion is not earlier; pending destruction after a prepared snapshot still requires replay. Restore points have a separate hard six-calendar-month maximum in `backup_recovery.md`; that maximum does not shorten this gate.

## 2. Data-Subject Requests
- **Erasure:** procedure response within **2 business days**; execution within **15 calendar days** of a valid request. In-app deletion enters `PENDING_DELETION` (7-day cancel window, all sessions revoked at request), then the erasure transaction runs. The DPO file records the request ID, operation ID and execution time for regulator inspection (A05, Bộ Công an).
- **Access / portability:** the only field-level export definition is `data_protection.md` § Access and Portability Requests, including reporter-own H and the separate operator-own request. This register and every API/runbook/test consumer reference that definition rather than reproducing category/field allowlists.
