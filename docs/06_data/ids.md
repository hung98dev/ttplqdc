# IDs
status: LOCKED

## Scope
Defines canonical identity classes, wire/database representations, generation, uniqueness scope, and serialization.

Persistence rationale: ../11_decisions/0011-postgresql-relational-persistence.md.

## Identity Classes
| Class | Example | Canonical representation |
|---|---|---|
| static content ID | skill.kim.kiem_quang | ASCII lowercase string |
| durable entity ID | account/character/guild/item/listing/claim | UUID v4 |
| operation ID | retriable value mutation | UUID v4 |
| runtime entity ID | monster/projectile/entity inside one owner lifetime | unsigned 64-bit integer scoped by owner/epoch |
| revision/counter | inventory_revision/session_epoch/ownership_epoch | unsigned monotonic integer |
| protocol message ID | message enum | stable numeric enum |

Do not substitute display names, array indexes, database row order, Unity instance IDs, or pointer addresses as persistent identity.

# Static Content IDs
Canonical form:
~~~
[a-z0-9]+(\.[a-z0-9_]+)+
~~~

Rules:
- ASCII only,
- lowercase,
- namespace segments separated by ".",
- words inside one segment use "_",
- immutable once shipped/persisted,
- localized Vietnamese display text is separate data,
- alias/deprecation migration is explicit; never silently rename a shipped ID.

## Region Token Split: `u_minh` vs `rung_u_minh`
The region token for U Minh Forest exists in two forms. This split is **intentional, stable, and must not be "fixed"**:

- `rung_u_minh` — canonical token in the `monster`, `zone`, `atlas`, and `drop` namespaces (e.g. `monster.rung_u_minh.*`, `zone.rung_u_minh.*`).
- `u_minh` — canonical token in the `item` and `set` namespaces (e.g. `item.u_minh.*`, `set.u_minh.*`).

The `item` and `set` IDs using `u_minh` are shipped stable IDs. Renaming them to `rung_u_minh` is prohibited by the immutability rule above; no alias entry is needed because no rename occurs. New IDs introduced in the `item` or `set` namespaces for this region use `u_minh`; new IDs in any other namespace use `rung_u_minh`. Content tooling must not flag this split as an inconsistency requiring repair.

# Durable IDs
Durable entity IDs use PostgreSQL uuid and RFC 4122 UUID v4 generated by authoritative Go code.

Generation:
- crypto/rand,
- set RFC 4122 version/variant bits,
- generation failure fails the operation,
- client may carry an assigned ID but cannot choose ownership by submitting an arbitrary UUID,
- no third-party UUID library is required.

Applies to at least account_id, character_id, session_id, guild_id, item_instance_id, reward_claim_id, auction_listing_id, auction_proceeds_id, trade_id, durable instance_id and audit_event_id. `operation_id` generation follows § Operation IDs.

A durable UUID is never reused after deletion.


## Composite Ownership Keys
Spirit beast ownership is 1:1 `(character_id, beast_id)` (ADR-0043). `beast_id` is a static content ID. There is no `beast_instance_id` UUID.
```text
character_beasts PK = (character_id, beast_id)
beast_equipment_locations PK = (character_id, beast_id, slot_id)
```

## Serialization
Canonical text form is lowercase 8-4-4-4-12 UUID.

PostgreSQL stores native uuid, not varchar(36).

Protobuf encodes every UUID as exactly 16 bytes (`bytes`, network order; `../05_network/protobuf_conventions.md` § 6, ADR-0064); HTTPS JSON uses the canonical lowercase text form.

# Operation IDs
Every retriable value-changing operation has one stable UUID generated once and reused across retries.

Generator (ADR-0065):
```text
client-initiated request (C2S message / HTTPS mutation)  client generates UUID v4 once per user intent and reuses it on retry;
                                                          server rejects nil, non-v4 or malformed IDs (`PROTOCOL_MALFORMED`)
server-initiated job / admin / webhook                    deterministic UUID v5 over SERVER_JOB_NAMESPACE_UUID and "<operation_family>:<job_key>"
                                                          (ADR-0070); job_key = the stable natural key of the job: account_id (erasure),
                                                          utc_date + scope (scheduled rollups/settlements), provider notification ID
                                                          (webhooks), audit_event_id of the recorded operator request (admin);
                                                          so a retry after a crash recomputes the same ID and nothing is persisted first
simulation settlement                                     deterministic UUID v5 (save_rules.md)
content grant                                             deterministic UUID v5 (§ Deterministic Content-Grant Idempotency Keys)
```
Uniqueness scope is `(operation_family, owner_id, operation_id)` (`data_model.md` § operations), so a client-chosen ID can never match another owner's operation.

Same operation ID + same operation family:
- same committed request -> return/reconstruct prior outcome,
- conflicting payload -> reject OPERATION_CONFLICT,
- never reroll/re-execute as a second logical mutation.

Do not use request timestamp as operation identity.

## Deterministic Content-Grant Idempotency Keys
Certain content grants — seasonal cosmetics, Atlas reward tiers, Guild Stone completions, and any future one-time content delivery — require a stable idempotency key that is derivable from structured inputs such as `(season_number, cosmetic_id, character_id)`. These keys must be stored in a PostgreSQL `uuid` column and satisfy all operation ID requirements, but must also be deterministically reproducible from the same inputs across retries and server restarts without persisting the key before the first attempt.

Rule: derive a **UUID v5** (RFC 4122 § 4.3) using SHA-1 over the project content-grant namespace UUID and the canonical grant-scope string. The result is a valid RFC 4122 UUID stored in a `uuid` column.

**Namespace UUID**: a project-defined namespace UUID generated once with `crypto/rand`, recorded in `../00_context/technology_versions.md` as `CONTENT_GRANT_NAMESPACE_UUID`. Do not use the RFC 4122 DNS or URL namespace UUIDs; use the project-specific constant.

**Grant-scope string**: a deterministic, globally unique dot-separated ASCII string defined per grant type by the owning system spec. Example for a seasonal cosmetic: `season.<season_number>.<cosmetic_id>.<character_id>`. The owning spec must document the exact format; the format must be deterministic and unique given the inputs.

**Derivation** (no third-party library required; uses Go standard library `crypto/sha1`):
```go
import "crypto/sha1"

func ContentGrantUUID(namespace [16]byte, grantScope string) [16]byte {
    h := sha1.New()
    h.Write(namespace[:])
    h.Write([]byte(grantScope))
    sum := h.Sum(nil) // 20 bytes
    var id [16]byte
    copy(id[:], sum[:16])
    id[6] = (id[6] & 0x0f) | 0x50 // version 5
    id[8] = (id[8] & 0x3f) | 0x80 // variant RFC 4122
    return id
}
```

This rule applies to every content grant needing a stable deterministically-reproducible idempotency key. A grant whose idempotency key cannot be derived from stable inputs must use a randomly generated UUID v4 stored durably before the first delivery attempt.

# Runtime Entity IDs
Transient simulation entities use unsigned 64-bit IDs scoped by:
~~~
simulation_owner_id + ownership_epoch + runtime_entity_id
~~~

They are unique for that owner/lifetime, never substitute for durable account/item/reward identity, and every client reference is revalidated against current owner/session/AOI/lifecycle.

# Monotonic Revisions / Epochs
Use 64-bit monotonic counters for server-owned revisions/epochs unless an owning protocol explicitly defines another bounded range.

Examples: inventory_revision, guild_revision, session_epoch, ownership_epoch, server_seq, client_seq.

Stale lower revision/epoch cannot regain authority.

# Names Are Not IDs
Character/guild names are user-facing Unicode and follow owning normalization/uniqueness rules. They never replace immutable UUID identity.

# Database Keys
A table may use a private surrogate numeric key only when it is purely storage-internal. Domain/wire ownership continues to use the canonical UUID. Private row IDs never become Unity authority.

# Validation
Reject malformed/zero UUIDs where a real ID is required, non-ASCII/uppercase static IDs, unknown closed namespaces, out-of-scope runtime references, and operation ID reuse with conflicting payload.

# Invariants
~~~
static ID = immutable ASCII lowercase string
durable domain ID = UUID v4
UUID generation = authoritative crypto/rand
runtime entity ID = owner/epoch-scoped uint64
revision/epoch = monotonic uint64
display name != identity
client-provided ID never bypasses ownership validation
deterministic content-grant idempotency key = UUID v5 derived from CONTENT_GRANT_NAMESPACE_UUID + grant-scope string
u_minh (item/set namespaces) and rung_u_minh (monster/zone/atlas/drop namespaces) are both stable shipped tokens; the split is intentional and permanent; no rename or tooling fix permitted
~~~
