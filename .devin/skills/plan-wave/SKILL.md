# Plan a Wave on Demand

Authority: `docs/10_implementation/wave_execution_prompts.md` § On-Demand Planning Contract owns the artifact sections, task-plan fields, dispositions and six quality checks; `agent_execution_protocol.md` §2–§2a owns readiness and the execution boundary. Read both first. This skill supplies the method, not another schema or task register. If sources disagree or a prerequisite is unavailable, report evidence and the owning role; never invent a rule to make a plan pass.

## Invocation boundary

- **Standalone planning:** an explicit “plan wave N” / “lập kế hoạch wave N” request returns planning artifacts and an independent audit only. It never implicitly becomes `/run-wave`, even with all tasks passing. Local `main` may be inspected without claims; unverified execution preconditions remain unresolved and cannot authorize dispatch.
- **Run-wave preflight:** “làm/chạy/do wave N” and `/run-wave` require this same planning-and-audit phase before any claim, implementation branch/draft PR, code or codegen. Only the coordinator resumes the existing execution workflow after this skill returns and the fresh DoR gate holds. Approval does not replace implementation PR review, `policy-review`, CI, evidence or the merge slot.
- **Skill-only invocation never claims, codes, changes task status or repository files, runs verification/application commands, accesses credentials or resolves BLK/OPS.** The planner's usable tools are `read`, `grep`, `glob` only. Session artifacts are responses/harness artifacts, not files committed into the repository. Do not generate plans for other waves or prewrite all waves.
- Inline skill `allowed-tools` only auto-approves reads; it is not a security sandbox. Capability enforcement comes from the actual planner/auditor custom profiles. Keep orchestration in the root coordinator (or its bounded nesting-enabled profile), not a planner subagent that cannot spawn the independent audit.

## Coordinator orchestration

These are coordinator responsibilities outside the read-only planner delegate; the skill does not grant execution or mutation capabilities.

1. Supply the requested N and the canonical inputs: a clean read-only `main` snapshot, recorded SHA, freeze/OPS state, active claims and resource reservations. Record how execution preconditions were verified and which remain unresolved. The coordinator obtains the SHA and external state; the planner must not execute Git, GitHub or shell commands to discover them. A missing/unproven snapshot identity is a finding, not a fabricated `planning_main_sha`.
2. Invoke `.devin/agents/wave-planner.md` through the native registered profile mechanism when the harness supports it, with this skill and the complete inputs. Do not guess CLI flags or claim native profile support without observing it. Otherwise delegate the **full profile and full skill instructions**, authority references and inputs to a dedicated read-only session restricted to `read`, `grep`, `glob`, with no GitHub credentials. Lack of a profile mechanism is not permission to skip planning. If no separate read-only delegate can be created, return the missing prerequisite and do not proceed to execution.
3. Obtain the complete canonical artifact; preserve each immutable revision and never attach an old audit to changed content. An unaudited artifact has no executable batches. Candidate plans include READY_TO_PLAN and only explicit eligible same-claim IN_PROGRESS `resume_task_ids` under the canonical input contract. If neither is eligible, return all-task readiness/findings with no handoffs or claims/code; do not substitute another wave.
4. Invoke `.devin/agents/wave-plan-auditor.md` in a **different context/session** from the planner, with the original snapshot, coordinator inputs and complete artifact/revision. This tool-restricted profile follows `.devin/agents/verifier.md` **Wave Plan Audit** mode with only `read`, `grep`, `glob`; do not use the normal exec-capable verifier profile for native plan auditing. Require the exact artifact reference, wave, `planning_main_sha` and `plan_revision`, not merely a passing verdict. Otherwise delegate the full audit profile, referenced verifier mode and authority instructions through a harness that actually restricts tools to read-only. No such independent capability → no dispatchable IDs. Do not pass tokens/App keys or run normal diff verification.
5. Process every finding. `REWORK` returns the full defect list to the planner for a complete corrected artifact, incremented `plan_revision` and another independent source-based audit. `BLOCKED` contract/authority gaps go to `spec-owner` as evidenced intake; environmental gaps go to the coordinator's existing OPS workflow. Neither delegate invents BLK/OPS IDs, edits specs/statuses or asks implementers to choose the missing decision. Keep every affected wave task and all its reasons in the artifact. Do not loop cosmetic rewrites around an unresolved prerequisite.
6. Return the complete artifact and matching audit with the exact `dispatchable_task_ids`; never infer eligibility from a wave-level score or from `READY_TO_PLAN` alone. IDs must have complete task plans, per-task `PASS` for this revision and no unresolved execution prerequisite. If a separate audit is unavailable, return the unaudited artifact and finding with no dispatchable IDs, never a passing gate. Partial wave readiness permits only the eligible audited tasks; retain all waiting/blocked/in-progress/done rows and findings.
7. For execution requests only, the coordinator rechecks fresh `main`, DoR, claims and resources before each claim/resume under §2–§2a. Relevant source or precondition changes regenerate affected plans and require a new audit. Unrelated changes or ordinary claim-field transitions require a recorded recheck, not a silent reuse or unnecessary redesign. Preserve `planning_main_sha`; supply the actual post-claim base SHA, branch/worktree, implementer and isolated resources in the canonical handoff. Assign one implementer per task and preserve the existing claim/bootstrap, concurrency, serialized integration and IMP-068 cutover rules. Do not rewrite the audited artifact to add execution facts and reuse its old audit: any artifact content change increments the revision and needs audit.

## Planner passes

The dedicated planner performs these passes against original sources, using reads/searches only. Read further relevant sections when the contract requires them; do not stop at the citations in an earlier plan.

### 1. Establish scope and readiness

- Read the complete `depends_on` DAG and derive the requested wave's membership; compare the canonical Waves table and topological order. A cycle, missing packet or grouping mismatch is an evidenced `spec-owner` finding, not a new dependency or guessed schedule.
- Read every requested-wave packet in full, direct dependency packets and their actual outputs, owning specs and listed ADRs, ADR Consequences that name those specs plus applicable amendments, live blockers, layout, conventions, pins and verification/evidence rules. A `PROPOSED` ADR cannot supply an accepted missing contract. Trace blocker applicability through owning specs, not just task IDs.
- Fill every canonical `Readiness` row from observed status/dependencies and §2 DoR evidence. Use exactly the canonical dispositions; retain both dependency-wait and blocking reasons when both exist. Planning dispositions do not mutate packet statuses or milestone states.
- Detailed task plans are only for READY_TO_PLAN or explicit eligible same-claim IN_PROGRESS resumes defined by the canonical Inputs and authority. Other in-progress/waiting/blocked/done rows receive source-backed accounting, no speculative handoff. Preserve existing claim/resources; missing proof is unresolved, never permission to reassign or dispatch.

### 2. Inventory semantics before designing steps

- Extract every obligation from `## Change`, every `## Acceptance` item/requirement ID, every named `## Tests` case, and generated artifacts, cleanup and evidence obligations in the whole packet. Split compound bullets into independently checkable obligations; follow referenced normative sections to the actual requirement, numbers and failure behavior.
- Parse a `Tests` section through its next real heading or packet metadata boundary, **not the first blank line**. Continue reading the rest of the packet for obligations after that boundary. Markdown headings of levels 1–6 are legal; fenced text does not create headings. Read prose, tables and fenced contracts, not only heading names or requirement-ID counts.
- Bind each inventory item to its original path + section/range at the snapshot and canonical requirement ID where present; otherwise use local source-bound labels as permitted by the contract. Do not mint project requirement IDs, task IDs or new scope. Put this traceability in the canonical `Coverage matrix`, not a second output schema.

### 3. Close contracts and verify reuse

- Trace each input/output to its producer and consumer and owning source. Resolve exact types, fields, signatures or approved schema references and check both ends agree on encoding/units, optionality, ordering and authority. Include validation/typed errors, bounds, state transitions, durable keys, idempotency, commit/ack timing, replay/rollback/restart and allocation/frame constraints where applicable; justify non-applicable cases from sources.
- Discover actual paths/symbols before claiming an API exists. Read the definitions and surrounding conventions of anything to reuse. Distinguish existing implementation, absent-but-owned authored outputs, generated files and editor-materialized outputs. A planned layout path is not existing code; a dependency marked `DONE` without its required usable output is a readiness gap.
- Missing product/wire/data contracts, contradictory producer/consumer contracts, unresolved ownership, unsupported pins or missing recovery rules are findings for the owning role. Never fill them with familiar defaults, phantom APIs, speculative dependencies, API scaffolds, shims, no-ops or decisions postponed to coding. Private helper names may be chosen only within the canonical contract's allowance, not to introduce a new external contract.

### 4. Make an executable handoff

- Build the canonical `File/API map` and `Ordered steps` from the closed contracts. Identify exact authored files/symbols/signatures, reuse locations and authoritative generators; include companion/generated/materialized outputs and their owners. Each step has local prerequisites, concrete change/algorithm, invariants and a stopping condition. Resolve allowed internal implementation choices here; do not leave “implement feature”, “handle errors”, “add tests”, or competing approaches for a weak implementer to design.
- Complete the `Coverage matrix` in both directions: each source obligation maps to concrete step IDs and observable verification; every step/output/test serves an in-scope obligation. Several obligations may share a step only if its actual change and verification satisfy all of them. Counts reveal omissions, never prove satisfiability.
- Design the canonical `Verification` from source-supported tooling: exact commands/platform/prerequisites, inputs and expected observable outcomes, applicable boundaries/errors/replay, codegen/drift/materialization and evidence/DONE/merge references. Include an actual runtime/UI/CLI scenario exercising the changed consumer path. Mark all checks **planned, not executed**; the planner and plan auditor never launch the application, runtime or tests. If the source cannot support an executable verification scenario, record the gap rather than invent a runner/API or claim CI passes.
- Reject source-text, mock-echo or tautological tests as behavioral proof. A useful check detects a plausible consumer-visible failure with deterministic inputs/assertions; a runtime smoke must observe the changed behavior, not only compilation. Respect canonical platform limits and accepted amendments rather than copying superseded CI matrices.
- Preserve complete task details, matrix, source references, stopping conditions and full matching audit for `Handoff`; a task ID, summary, ellipsis or “see other task” is not an implementer prompt. If transport requires chunks, provide numbered continuations of the same session artifact with the same identity/revision and all canonical sections, and ensure the coordinator/verifier/implementer receives every chunk. An incomplete delivery has no eligible dispatch; never truncate obligations to fit a prompt.

### 5. Self-critique, then return for independent audit

Read the original inventory again, independently of the drafted steps. Apply **all six canonical quality checks** to each task, challenge success-only assumptions and examine failure/recovery ordering and producer/consumer compatibility. Look for omitted compound clauses, tests after blank lines, nonexistent symbols, unowned outputs, lossy handoffs and unresolved reservations. Repair plan-quality defects before submission; record irreducible gaps in canonical `Findings` and exclude affected tasks from dispatch. Return the complete canonical artifact, never a planner-issued `PASS`, a promise of perfection or executed evidence.
